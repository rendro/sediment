# Repository Audit Report — 2026-01-31

Comprehensive audit of the Sediment codebase covering security, data integrity, concurrency, and robustness.

---

## Critical Issues

### 1. `expire_item` is not crash-safe (data loss risk)
**File:** `src/db.rs:756-803`

`expire_item` deletes the item row then re-inserts it with updated `expires_at`. If the process crashes between delete and insert, the item is permanently lost. The retry logic only covers insert failures within the same process — a crash or OOM between the two operations is unrecoverable.

**Recommendation:** Use LanceDB's update mechanism if available, or maintain a write-ahead log entry before the delete so recovery can replay the insert.

### 2. `get_co_accessed` returns input IDs as neighbors
**File:** `src/graph.rs:275-327`

Unlike `get_neighbors` (which filters input IDs at line 223), `get_co_accessed` does not filter out the queried IDs from results. If items A and B are co-accessed, querying co-access for `[A]` can return A itself as a suggested item. This leads to duplicate results in the `suggested` array of recall responses.

### 3. Background consolidation merge fetches items twice with no consistency
**File:** `src/consolidation.rs:239-255, 259-260`

`process_candidate` calls `db.get_item()` for both items to compute fresh similarity, then calls `db.get_item()` again for the merge. Between these two fetches, items could be modified (via `replace`) or deleted. The second fetch could return different data or `None`, leading to stale similarity decisions or silent skips.

### 4. Similarity score semantics are misleading
**File:** `src/mcp/tools.rs:599-613`

After decay scoring and trust bonus, the `result.similarity` field is overwritten with a composite score (`base_score * trust_bonus`). This composite score is then returned to the MCP client as `"similarity"`. Consumers expect this to be a cosine similarity in [0, 1], but the trust bonus can inflate it (capped at 1.0, so high-trust items saturate). This conflation makes the score unreliable for downstream thresholding.

## Security Issues

### 5. No size limit on recall query strings
**File:** `src/mcp/tools.rs:717`

The `store` tool enforces a 1MB content limit, but `recall` has no limit on query string length. An adversarial MCP client can send a multi-megabyte query, causing the embedder to allocate large token tensors and consume excessive CPU/memory.

**Recommendation:** Add a query length cap (e.g., 10KB) in `execute_recall`.

### 6. Rate limiter is trivially bypassable and per-process only
**File:** `src/mcp/server.rs:218-238`

The rate limiter state lives in-process memory. Restarting the server (or running multiple instances) resets or bypasses it entirely. For a local-first tool this is low severity, but if the server is ever exposed over a network transport, this provides no real protection.

### 7. Provenance leaks filesystem paths
**File:** `src/mcp/tools.rs:414`

Every stored item injects `_provenance.project_path` containing `ctx.cwd.to_string_lossy()`, which is the full filesystem path of the working directory. If items are ever shared or exported, this leaks the user's directory structure.

### 8. `sanitize_sql_string` is ad-hoc and fragile
**File:** `src/db.rs:11-13`

The function escapes `\` and `'` for LanceDB SQL filter expressions. This is a hand-rolled sanitization that doesn't account for all SQL special characters (e.g., `%`, `_` in LIKE contexts, null bytes). While LanceDB's filter DSL may not support LIKE, if that ever changes, this becomes exploitable. Parameterized queries would be safer where LanceDB supports them.

## Data Integrity Issues

### 9. `delete_item` has a TOCTOU race
**File:** `src/db.rs:807-834`

`delete_item` calls `get_item` to check existence, then deletes. If another operation (e.g., consolidation) deletes the item between the check and the delete, `delete_item` returns `true` (indicating deletion) even though it deleted nothing. The chunks deletion also silently succeeds on a no-op.

### 10. Corrupted timestamps silently become "now"
**File:** `src/db.rs:1184-1197`

When reading `expires_at` and `created_at` from Arrow arrays, invalid timestamps (e.g., out of range) fall through to `unwrap_or_else(Utc::now)`. This silently converts corrupted data into the current time, masking database corruption and potentially un-expiring items that should be expired.

### 11. `chunk_index` cast from i32 to usize wraps on negative values
**File:** `src/db.rs:1284`

`chunk_index_col.value(i) as usize` — if the stored value is negative (corrupted data), this wraps to a very large `usize`. While unlikely in normal operation, corrupted data would produce silently wrong chunk ordering.

### 12. Consolidation stores content in edge `rel_type` field
**File:** `src/consolidation.rs:299`

When merging, the removed item's content (up to 500 chars) is stored in the `rel_type` column as `"merged_archive:<content>"`. The `rel_type` field is a TEXT column with no length constraint, but this mixes data (content) with metadata (relationship type). If the content contains special characters, it could cause issues in downstream queries that parse `rel_type`.

### 13. Auto-tag inference can produce stale results
**File:** `src/mcp/tools.rs:435-460`

Auto-tag inference calls `find_similar_items` before the new item is stored. Then `store_item` internally calls `find_similar_items` again for conflict detection. These two calls may see different database states if concurrent stores are happening, leading to inconsistent tag inference vs. conflict detection.

## Concurrency Issues

### 14. Multiple independent SQLite connections to `access.db` with no coordination
**Files:** `src/access.rs`, `src/graph.rs`, `src/consolidation.rs`

Each tool call opens separate `AccessTracker`, `GraphStore`, and (sometimes) `ConsolidationQueue` connections to the same `access.db` file. Background tasks (`spawn_logged`) also open their own connections. While WAL mode and `busy_timeout=5000` mitigate most contention, heavy concurrent recalls can cause `SQLITE_BUSY` errors on write-heavy operations (co-access recording, consolidation).

### 15. Background tasks for co-access, clustering, and cleanup have no concurrency guards
**File:** `src/mcp/tools.rs:811-873`

Consolidation uses a `Semaphore(1)` to prevent concurrent runs. But co-access recording, clustering, and expired cleanup have no such guards. Rapid successive recalls can spawn overlapping co-access recordings and cleanup tasks, causing SQLite write contention.

### 16. `get_or_create_project_id` is not atomic on Windows
**File:** `src/lib.rs:168-191`

The write-temp-then-rename approach relies on atomic rename, which is guaranteed on Unix but not on all Windows filesystems. On Windows, the re-read after rename could see a partially written file, causing a JSON parse failure that falls through to returning the in-memory UUID (which may differ from what's on disk).

## Robustness Issues

### 17. `get_expired_item_ids` panics on schema mismatch
**File:** `src/db.rs:923`

`id_array` is accessed via `.unwrap()` after a `downcast_ref`. If the column type ever changes or LanceDB returns an unexpected schema, this panics rather than returning an error.

### 18. No input validation on tags, titles, or source fields
**Files:** `src/mcp/tools.rs:398-432`

There's no length limit or content validation on `tags`, `title`, `source`, or `metadata` fields (beyond the 1MB total content limit). An adversarial client could store items with thousands of tags, megabyte-long titles, or deeply nested metadata objects, impacting storage and search performance.

### 19. `detect_content_type` can misclassify content
**File:** `src/db.rs:972-1043`

The heuristic-based content type detection has edge cases:
- Content starting with `const ` or `let ` (JavaScript keywords) is detected as Code even if it's prose like "let me explain why const means constant"
- The YAML detection was improved but still triggers on 2+ lines matching `key: value` patterns, which could match structured prose

### 20. Decay scoring formula is documented as "half-life ~30 days" but isn't exponential
**File:** `src/db.rs:941-943`

The freshness formula `1.0 / (1.0 + age_days / 30.0)` is a hyperbolic decay (Lorentzian), not exponential. At 30 days, freshness = 0.5 (correct), but at 60 days it's 0.33 (exponential would be 0.25). Items decay significantly slower than an exponential half-life suggests. The documentation should be corrected or the formula changed.

### 21. No query result deduplication in `get_co_accessed`
**File:** `src/graph.rs:284-293`

The SQL query uses `IN` clauses that can match both `from_id` and `to_id` for the same edge row (when both endpoints are in the query set). The `CASE WHEN from_id IN (...) THEN to_id ELSE from_id END` expression returns one side per row, but with multiple input IDs, the same neighbor can appear multiple times from different edges. While there's deduplication at line 322-324, it happens after collecting all results, which could be expensive with large graphs.

### 22. `recall_count` overflow
**File:** `src/mcp/tools.rs:822-824`

`recall_count` is an `AtomicU64` incremented with `Relaxed` ordering on every recall. The modulo check `run_count % 10 == 9` works correctly, but after 2^64 recalls the counter wraps to 0. This is practically unreachable but worth noting as a theoretical concern.

## Minor Issues

### 23. `Embedder` thread safety claim should note mutex-free design
**File:** `src/embedder.rs:22-24`

The doc comment says `BertModel` and `Tokenizer` are `Send + Sync`, but `Embedder::embed` takes `&self` and runs inference synchronously. If the server ever moves to multi-threaded request handling (e.g., async MCP), concurrent `embed` calls would be safe but could interfere at the BLAS level depending on the Candle backend.

### 24. `truncate` is O(n) in character count
**File:** `src/mcp/tools.rs:1041-1052`

`s.chars().count()` iterates the entire string, then `char_indices().nth()` iterates again. For the 80-100 character limits used, this is negligible, but for large strings it's wasteful. Since it's only used on preview/truncation paths, impact is minimal.

### 25. Consolidation queue has no index on `status` column
**File:** `src/consolidation.rs:39-51`

`fetch_pending` filters by `status = 'pending'` and `cleanup_processed` filters by status, but there's no index on the `status` column. With a large queue, these queries become full table scans.
